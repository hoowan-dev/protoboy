# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

ProtoBoy is a game-dev prototyping companion: living docs, asset lifecycle tagging, project health checks, and toolchain integration (the plugin currently implements docs, MCP and task boards; see Architecture). The full concept and roadmap are in the Obsidian vault at `C:\Users\becer\Documents\Obsidian\Hoowan Vault\Code\ProtoBoy\ProtoBoy Ideas.md`. Read it before adding features: the code is organized by the "pillars" defined there.

The repo currently contains only the Unreal Engine 5.9 editor plugin (`Unreal/ProtoBoy`). It is intentionally a base: most functions are stubs marked `// TODO` that describe the intended behavior. Keep new work simple and stub-first unless asked to implement something fully. Future engines and the daemon go in sibling top-level folders (`Unity/`, `Godot/`, `Daemon/`).

## Build

UE 5.9 is installed at `C:\Program Files\Epic Games\UE_5.9`. There is no host project in the repo; build the plugin on its own with BuildPlugin. Package to a temp/scratch folder, never inside the repo:

```
"C:\Program Files\Epic Games\UE_5.9\Engine\Build\BatchFiles\RunUAT.bat" BuildPlugin -Plugin="C:\dev\protoboy\Unreal\ProtoBoy\ProtoBoy.uplugin" -Package="<temp dir>" -TargetPlatforms=Win64
```

- Do **not** pass `-NoHostPlatform`. It skips the editor target, so the editor-only module never compiles and the build "succeeds" without checking anything.
- Success means `BUILD SUCCESSFUL` and `UnrealEditor-ProtoBoy.dll` in `<temp dir>/Binaries/Win64/`. When filtering output, grep for `error|warning C|BUILD SUCCESSFUL|ExitCode`.
- Check engine APIs against the headers under `Engine/Source` rather than from memory, since 5.9 may differ from older versions.
- **Unity builds:** the editor merges the module's .cpp files into `Module.ProtoBoy.cpp`, so file-local names collide across files. Never put `using namespace` at file scope, and don't use anonymous namespaces for helpers: put them in a namespace named after the file (e.g. `ProtoBoyTrello`) and call them qualified. Helpers shared by several files go in a shared header (e.g. `Private/Net/PBHttpServerUtils.h`).
- BuildPlugin does **not** catch unity collisions: adaptive unity compiles files modified in git separately. To check, copy the plugin into a scratch host project (`<scratch>/Host/Plugins/ProtoBoy` plus a minimal `.uproject` enabling it) and run `"C:\Program Files\Epic Games\UE_5.9\Engine\Build\BatchFiles\Build.bat" UnrealEditor Win64 Development -Project="<scratch>/Host/Host.uproject" -DisableAdaptiveUnity`; the output should show a single `Module.ProtoBoy.cpp`.

- **`FString::Find` clamps its start position** to the last character, so searching from `Len()` finds a trailing match again. In line loops use `ProtoBoyMarkdown::Detail::FindLineEnd` (Docs/PBMarkdown.cpp) or stop at `Len()` before calling `Find`; otherwise any doc ending in a newline loops forever (this froze the editor at startup once).

There are no tests or lint setup yet.

## Architecture

Source files use a `PB` prefix (`PBSubsystem.h`, `SPBDashboard.cpp`); class names keep the full `ProtoBoy` prefix. `ProtoBoy.Build.cs` must match the module name and is not renamed.

Single module `ProtoBoy` (Type `Editor`, `PostEngineInit`).

- `FProtoBoyModule` handles only editor UI registration: the `ProtoBoyDashboard` nomad tab and the **Tools > ProtoBoy Dashboard** menu entry (via `UToolMenus` startup callback, owner-scoped so shutdown unregisters it).
- `UProtoBoySubsystem` (a `UEditorSubsystem`) is the central hub. It owns one plain C++ service per pillar as `TUniquePtr` and is where editor events (asset registry, package save, live coding) should be bound and routed (`BindEditorEvents`, currently a TODO). Access it with `UProtoBoySubsystem::Get()`.
  - **Product goal:** keep AI agents' work aligned with the game's architecture, design docs and task board, so they don't build monolithic or goal-less code. Layers: sources (provider interfaces) -> model (the doc map: Vision, Overview, Design / Tech docs, ADRs; linked tasks) -> MCP tools -> workflows (agent guide, server instructions, prompts).
  - `IProtoBoyDocsProvider` (Docs/PBDocsProvider.h): docs storage. `FProtoBoyFolderDocsProvider` (Markdown files under a root, path-checked) backs both `FProtoBoyObsidianDocsProvider` (Docs/Obsidian/) and `FProtoBoyLocalDocsProvider` (`DocsDirectory`). Get the active one with `UProtoBoySubsystem::GetDocsProvider()`.
  - `FProtoBoyDocGenerator` (Docs/): pillar 1 docs service over the active provider: the plain layer under the doc map. Search, `CreateDoc`, `AppendToSection`, `SetManagedBlock`, `CreateADR` (`ADR/ADR-NNNN-*.md`, written with Decision frontmatter). Vision and Overview setup UI is in the Obsidian page of Connect to Documentation and on the doc map; the dashboard's Setup page only shows status. MCP tools guard the Vision and Overview (append only) by layer, not by path. Writes never rewrite human text: append, new files, or `<!-- protoboy:begin id -->` managed blocks (`ProtoBoyMarkdown`, Docs/PBMarkdown.h).
  - `FProtoBoyDocMap` (Docs/PBDocMap.h): the doc map, the project's docs as layers (`EProtoBoyDocLayer` in Docs/PBDocLayers.h: Vision > Overview > Design (nestable) > Tech (pairs with a Design doc) / Systems / Content / Direction / Decision). **The docs are the model:** each doc's layer, stable id and links live in its own YAML frontmatter (`protoboy-id`, `protoboy-layer`, `protoboy-parent`, `protoboy-implements`; keys in `ProtoBoyDocLayers`, parsed and written by `ProtoBoyMarkdown::ParseFrontmatter` / `SetFrontmatterValues`, which keep the team's other properties), and the map is rebuilt by reading every doc (`Refresh`, also on docs connection changes; lazy on first use). There is no separate model file, so never add one: write changes into the docs. ADRs in `ADR/` count as Decisions even without frontmatter; other docs without a layer are listed by `GetUnmappedDocs` and put on the map with `AddToMap`. Tree: the first Vision is the root; a doc's parent is its `protoboy-parent` if that names another doc, else the layer default (`GetDefaultParent`: Overview under the Vision, Tech under the Design doc it implements, everything else under the Overview), resolved once per load with loops broken (`ResolveParents`); use `GetParent` / `GetChildren`, never the raw `ParentId`. Default parents aren't written, so `SetParent` clears the key when a doc goes back to its default. No rules restrict which layer sits under which. New docs come from their layer's sections (`ProtoBoyDocLayers::GetHeadings`, hints as HTML comments so they're hidden in Obsidian and stripped by `ProtoBoyMarkdown::StripComments` when reading); `CreateDoc` nests Design docs in folders (`Design/Combat/Weapons/Weapons.md`) and puts the other layers in one folder each; `CreateTechDoc` writes `<Design>.tech.md` next to the Design doc with one section per `##` section of it. `CreateVisionAndOverview` writes `Vision.md` / `Overview.md` (they replace the old Architecture doc; the docs setup check needs both). Every write refreshes the map and rewrites the Overview's managed `areas` block (`UpdateOverviewIndex`), then fires `OnChanged`. `ReadVision` parses pitch / player fantasy / `###` design pillars (skipping `Example`) / non-goals for `get_project_context`. UI: `SProtoBoyDocMapEditor` (UI/Docs/Map/), a Behavior Tree style `SGraphEditor` graph (`UProtoBoyDocMapGraph` / `UProtoBoyDocMapGraphNode` / `UProtoBoyDocMapGraphSchema`, a transient view rebuilt after every change, deferred a frame since changes arrive inside graph callbacks; node widget `SProtoBoyDocMapNode` reuses the AIGraph module's `SGraphPinAI` and `FAIGraphConnectionDrawingPolicy`). Moving a doc on the map only changes its frontmatter, never its file. The old pillar tree (`FProtoBoyPillarService`, `Pillars.json`, pillar templates and their dialog) was replaced by this; it's in git history (commit 1139b1f). `Resources/PillarTemplates/` and `Scripts/make_pillar_templates.py` are left from it and unused until doc-set templates replace them.
  - `IProtoBoyTaskProvider` (Tasks/PBTaskProvider.h): async task board API (callbacks on the game thread). `FProtoBoyTrelloClient` (Tasks/Trello/) implements it, limited to the team's board and list mapping in `UProtoBoySettings` (`TrelloBoardId`, `Trello*ListId`, set in the Trello panel). Tasks link a design doc with a `Design doc: <path>` line. Get it with `UProtoBoySubsystem::GetTaskProvider()`.
  - Outgoing HTTP goes through `ProtoBoyHttp::SendRequest` (Private/Net/PBHttpClient.h): completes on the HTTP thread, callbacks run from a queue the subsystem pumps (core ticker + modal tick).
  - `FProtoBoyObsidianConnector` (Docs/Obsidian/): file-system link to an Obsidian vault (a folder with `.obsidian/`). Finds vaults via `%APPDATA%/obsidian/obsidian.json`, validates, creates the docs folder and a `_ProtoBoy.md` marker note, and saves the connection through `FProtoBoyDocsConnectionStore`. UI lives in `SProtoBoyObsidianPanel` (UI/Docs/Obsidian/). Platform-specific code goes in a per-platform subfolder of its feature (`Docs/<Platform>/`, `UI/Docs/<Platform>/`); shared docs code stays in `Docs/`.
  - `ProtoBoyAssetSourcing` (Sourcing/PBAssetSourcing.h): pillar 3 asset *sourcing* only. Everything about sourcing lives under `Sourcing/` (each source in `Sourcing/<Source>/`, e.g. `ProtoBoyFab` in `Sourcing/Fab/`), its MCP tools and prompts in `Private/Sourcing/PBSourcingMCP.cpp` (registered from the central MCP registries), and its UI in `UI/Sourcing/`. Team settings (Asset Sourcing category) say whether agents should avoid AI-generated assets, which sources are enabled (Fab today) and where the art direction doc is; `DescribePolicyForAgents()` feeds `get_project_context` and the agent guide. Fab has no public search API, so `fab_search` only builds a fab.com search URL and opens it in the user's browser; never fetch or scrape Fab listings. Tools tied to a source use `FProtoBoyMCPTool::IsAvailable`.
  - Asset lifecycle tagging / Greybox Replacement Matrix (rest of pillar 3) and pillar 4 (health checks, Prototype-to-Production Viability Index) are **removed for now**. Don't re-add them unless asked; the old stubs (`FProtoBoyAssetLifecycle`, `FProtoBoyHealthChecker`) are in git history.
  - `FProtoBoyTrelloConnector` (Tasks/Trello/): Kanban task board link. One-click connect: opens `trello.com/1/authorize` with the API key from `UProtoBoySettings::TrelloApiKey` (else a built-in key), Trello redirects to a short-lived page on `127.0.0.1:<TasksCallbackPort>` that POSTs the token (from the URL fragment) back with a one-time state value; the token is verified against `/1/members/me` and saved per user via `FProtoBoyTasksConnectionStore` (`Saved/ProtoBoy/TasksConnection.json`). The key's Power-Up must allow that origin. UI is `SProtoBoyConnectTasksDialog` (UI/Tasks/) with provider panels in UI/Tasks/<Provider>/.
  - Modal windows: Slate's modal loop doesn't tick the core ticker, so local HTTP listeners and game-thread HTTP completions stall while one is open. `UProtoBoySubsystem::OnModalLoopTick` pumps them; outgoing requests use `CompleteOnHttpThread` and hand results to the game thread.
  - `FProtoBoyDaemonClient` (Daemon/): link to the planned engine-agnostic daemon over local WebSocket.
  - `FProtoBoyMCPServer` (MCP/): ProtoBoy as an MCP server on `127.0.0.1` that agents (Claude Code, Claude Desktop, Gemini CLI) connect to and call ProtoBoy tools; ProtoBoy holds no LLM API keys. Streamable HTTP via the engine's `HTTPServer` module (handlers run on the game thread). Dual-era: modern stateless requests (2026-07-28, per-request `_meta`, mirrored `Mcp-*` headers validated) and legacy `initialize`-handshake clients (2025-03-26..2025-11-25) on the same `/mcp` endpoint. Modal windows stall the core ticker; see the modal note below. Owns the tool list and the per-user bearer token (saved by `FProtoBoyMCPConnectionStore` to `Saved/ProtoBoy/MCPConnection.json`). `FProtoBoyMCPClientConfig` adds/removes ProtoBoy's entry in each client's config (JSON merge with a `.protoboy.bak` backup; Claude Code via the `claude mcp` CLI) and builds the manual-setup snippet; `FProtoBoyMCPServer::ConnectClient` is the one-click entry point. Team-wide options (port, write-tool gating, disabled tools) live in `UProtoBoySettings`. UI is `SProtoBoyConnectLLMDialog` and its panels in UI/MCP/. Intended to move into the daemon later.
    - Tools are registered in `MCP/PBMCPTools.cpp` (input schema + async handler; call `Done` exactly once); schema and argument helpers are in `MCP/PBMCPToolHelpers.h`. Feature areas register their own tools and prompts (e.g. `ProtoBoySourcingMCP`). Prompts (`plan-feature`, `implement-task`, `record-decision`) in `MCP/PBMCPPrompts.cpp`. Server instructions in `PBMCPServer.cpp`.
    - Write tools need `bAllowMCPWriteTools`; with `bConfirmMCPWriteTools` each call waits for Allow/Deny on an editor notification (`FProtoBoyMCPApprovals`, denied after 120 s). Every write is logged to `Saved/ProtoBoy/AgentActivity.jsonl` (`FProtoBoyAgentActivityLog`).
    - Connect also writes a managed `agent-guide` block into the project's `CLAUDE.md` / `GEMINI.md` (`ProtoBoyAgentGuide`), the always-loaded workflow guidance.
- UI mirrors the feature folders: each feature's windows and panels go under `UI/<Feature>/` (`UI/Docs/`, with the doc map in `UI/Docs/Map/`, `UI/MCP/`, `UI/Tasks/`, `UI/Sourcing/`); only the dashboard and `PBStyle` sit directly in `UI/`.
- `UProtoBoySettings` (`UDeveloperSettings`, `Config=ProtoBoy`, `DefaultConfig`) holds all tunables and saves to the host project's `DefaultProtoBoy.ini`. Add new options here rather than hard-coding them. Machine-specific state (absolute paths, per-user connections) does not go here, since that ini is committed.
- `FProtoBoyDocsConnectionStore` (Docs/PBDocsConnection.h) serializes the user's documentation connection (`FProtoBoyDocsConnection` USTRUCT, via `FJsonObjectConverter`) to `<Project>/Saved/ProtoBoy/DocsConnection.json`. Add fields to the struct; bump `CurrentVersion` only for breaking changes. `FProtoBoyObsidianConnector::OnConnectionChanged` fires after Connect/Disconnect so UI can refresh.
- The service headers are included directly in `PBSubsystem.h`, not forward-declared. UHT-generated code destroys the `TUniquePtr` members, and forward declarations there fail with C4150 (incomplete type).
- Design intent from the concept doc: docs are human-readable Markdown that must survive human edits (regenerate only auto-generated blocks), and heavy analysis is meant to move to the daemon eventually so the editor stays responsive.
